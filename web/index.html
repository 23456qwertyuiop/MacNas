目录结构

MacNas

一个跑在自己 Mac 上的私人 NAS。没有第三方依赖， 文件按内容哈希去重存储，逻辑目录只存在于索引里 —— 所以同一份内容无论放多少次、跨几个目录，磁盘上都只有一份。

从原理看起 看目录结构
01

先讲清楚：为什么不直接把文件放进文件夹

这是整个设计的地基，其它所有取舍都从这里推导出来。

最常见的做法是让磁盘结构和你在网页里看到的目录一一对应：网页里的 /照片/2026/海边.jpg 就等于磁盘上的 document/照片/2026/海边.jpg。这样最直观，但会带来三个绕不过去的问题：

重复内容占多份

同一个文件复制到两个目录，磁盘就存两份。用户的「复制」和「备份」习惯会让占用迅速膨胀， 而你其实只需要保留一份内容 + 两条指向它的记录。

改名与移动变成真搬字节

移动一个 8GB 的目录要真的把 8GB 读出来再写回去，慢、费电、还容易在中途失败留下半个状态。

结构一旦定下就难改

如果磁盘结构 = 用户看到的目录，那任何一次「目录语义调整」都等于一次全盘数据迁移。

MacNas 的选择：把「内容」和「名字」彻底分开。 磁盘上只存内容（按内容哈希命名）， 你看到的目录树只是一份索引记录 —— 于是复制不占空间、改名移动只改一行 JSON、删除只需减引用计数。

02

存储原理：内容寻址 + 索引记录

每个目录（卷）里只有两份东西：document/ 存内容，info/ 存记录。

一个已初始化的目录（卷）
/Users/你/我的资料            ← 你选的目录
├── document/                 ← 只有内容，按哈希分桶
│   └── blobs/
│       ├── b3/
│       │   └── 25d290026b65fcf5a8fc87c1ef088f…1e53.docx
│       └── 7f/
│           └── 83a1c9e4…（另一份内容）
└── info/                     ← 只有记录
    ├── index.json            ← 逻辑目录树 + 文件记录
    ├── index.json.bak        ← 上一次的可用副本
    ├── volume.json           ← 这个目录的身份标记
    └── shares.json           ← 分享链接

注意：磁盘上没有 照片/、项目/ 这些文件夹。 它们只活在 info/index.json 里。哈希前两位做目录（b3/）只是为了 避免一个目录塞进几十万个文件。

一次上传发生了什么

  1. 边收边算哈希：请求体直接流式落盘到临时文件，同时增量计算 SHA-256（不占内存）。
  2. 查重：拿到哈希先看 document/blobs/<前两位>/<完整哈希> 是否已存在。
  3. 命中就丢弃临时文件：内容已经在库里了，只写一条记录 —— 这一步就是「秒传」和「去重」。
  4. 未命中则改名入库：把临时文件原子地移动到哈希路径。
  5. 写记录：在 info/index.json 里加一条 {id, name, logicalPath, sha256, size, createdAt}。

记录里的 logicalPath 才是「它在哪个目录、叫什么名字」。

四个日常操作的真实代价

操作实际发生的事是否搬字节
上传重复内容算哈希 → 命中 → 只写一条记录不搬
复制文件/文件夹新增记录（内容引用计数 +1）不搬
改名 / 移动改记录里的 logicalPath不搬
删除一份删记录，引用计数归零才删内容可能删

去重是跨所有已添加目录的全局去重：同一个内容在 A 盘和 B 盘只需要存一份， 记录里会标明它实际落在哪个卷上。

逻辑目录树 ↔ 物理内容
网页里看到的
/
├── 照片/
│   ├── 海边.jpg      sha256 = 7f83a1…
│   └── 备份/
│       └── 海边.jpg  sha256 = 7f83a1…（同一个哈希！）
└── 项目/
    └── 报告.docx     sha256 = b325d2…
→
磁盘上真实存在的
document/blobs/
├── 7f/83a1c9e4…      1 份内容，被 2 条记录引用
└── b3/25d290026…     1 份内容，被 1 条记录引用

两张「海边.jpg」在网页上是两个文件，在磁盘上只有一份。 删除其中一张，另一张照样能打开；两张都删掉，内容才会被回收。

03

冻结的磁盘契约：让后续更新不改动已有数据

磁盘格式一旦发布就不能乱动 —— 用户的资料已经在里面了。

MacNas 把「磁盘长什么样」当成一份对外契约固定下来，用五条规则保证任何新版本都能安全地读写老数据：

1

卷根只允许两份东西

document/ 与 info/。不新增第三种顶层目录，也不改名。 名字写在 StorageLayout 里作为常量，代码任何地方都不许拼字符串绕过它。

2

字段只增不改、不删

新增能力只能增加 JSON 字段。已有的字段名、含义、类型永不改变 —— 老版本读到新字段不认识时，会原样保留而不是丢掉。

3

未知字段原样保留

写入索引前会做一次「合并」：新版本不认识的老字段、以及其它工具写进去的自定义字段， 都会原封不动地写回去。这样多个版本交替打开同一个目录也不会互相破坏。

4

版本号 + 只读降级

每份索引都带 formatVersion（当前为 1）。 如果打开了一个比自己更新的版本，MacNas 会只读挂载： 浏览、下载、预览都正常，任何写入操作返回 409，一个字节都不改。

5

索引可以丢，内容不能丢

因为文件名就是内容哈希，所以就算 info/index.json 彻底损坏， 也能扫描 document/blobs/ 重建出记录（文件名 → 哈希 → 大小）。 写入时先写临时文件再原子替换，并保留上一份 index.json.bak 兜底。

这套约定的意义：软件的升级永远不会要求用户迁移数据。 新功能要么是新增字段（老版本忽略它），要么是新增只读能力； 不会出现「升级后旧目录打不开」或「老版本打开新目录把数据写坏」。

04

服务器：手写 HTTP/1.1，零第三方依赖

用系统自带的 Network.framework 从 TCP 开始实现，不引入任何包。

请求是怎么被处理的

  1. NWListener 监听端口，每条新连接分配独立队列（这一点很关键，见下）。
  2. 字节流先做 HTTP/1.1 解析：请求行、头部、Cookie、查询参数。
  3. 请求体按需处理：普通接口读进内存（有限额），上传则交给流式落盘 + 增量哈希的 sink。
  4. 路由分发：静态资源 → 网页壳；/api/… → 业务接口（需要登录态）；/dav → WebDAV。
  5. 响应支持普通长度与文件流：下载/预览走文件流，并支持 Range 断点续传。

三个踩过坑才定下来的细节

每条连接一个队列

最初所有连接共用一条串行队列，结果是：macOS 挂载 WebDAV 时会同时开十几条连接探测， 排在后面的被前面的请求堵住而超时，挂载直接失败。改成每连接独立队列后才正常。

密码验证必须够快

PBKDF2 用系统 CommonCrypto 实现（输出与手写实现逐位一致，所以老配置不用迁移）， 单次从 182ms 降到 15ms —— 因为 macOS 的 WebDAV 客户端对单个请求只有约 300ms 容忍上限。

上传不经过内存

大文件上传时请求体直接写入临时文件并同时计算哈希，内存占用与文件大小无关。

接口一览

方法路径作用
POST/api/login · /api/logout登录，发放会话 Cookie
GET/api/volumes · /api/list目录列表与卷（已添加目录）信息
POST/api/upload流式上传 + 去重
GET/api/download下载（支持 Range）
GET/api/preview · /api/preview/content预览信息与预览内容
POST/api/mkdir · /api/rename · /api/delete · /api/transfer新建目录、改名、删除、复制/移动
GET/api/search全局搜索（文件名与路径，多关键词）
POST/GET/api/share/create · /api/shares创建与管理分享链接

GET/api/pub/<token>/…分享页匿名访问：信息、密码校验、下载、预览
05

WebDAV：把逻辑目录树挂载成网络磁盘

Finder 里 ⌘K → http://你的IP:端口/dav，就能像本地磁盘一样读写。

WebDAV 直接实现在同一个 HTTP 服务器里，映射的不是磁盘上的哈希文件，而是 info/index.json 里的逻辑目录树。所有写操作走的还是同一套去重管线， 所以从 Finder 拖进去的文件同样会自动查重、并立刻出现在网页端。

挂载时的握手顺序

  1. OPTIONS /dav — 客户端探测服务器能力（必须免认证返回 200）
  2. OPTIONS /dav/ — 文件系统层接手
  3. PROPFIND /dav/ — 列目录 → 此时才返回 401 挑战
  4. 客户端弹出账号密码框 / 用已保存的凭据重试
  5. PROPFIND → 207 目录清单，挂载完成

一个反直觉的坑

第一版里，未认证的 OPTIONS 也返回 401。结果是 Finder 在「手上还没有凭据」时 会一直重试这个探测请求，最后直接报「连接服务器出现问题」， 永远不会走到弹密码框那一步。

对照实验：同一个响应体，由「要求认证」的服务器发出 → 客户端只发 3 个请求就放弃； 由「OPTIONS 免认证」的服务器发出 → 客户端立刻推进到 PROPFIND。 所以现在 OPTIONS 免认证返回能力声明（只暴露协议能力，不含任何文件信息）。

支持的方法

OPTIONS · GET · HEAD · PUT · MKCOL · DELETE · MOVE · COPY · PROPFIND · PROPPATCH · LOCK · UNLOCK

支持 Range（拖动播放/断点续传）与 ETag； LOCK 返回合法锁令牌但不做真正互斥（单用户私人 NAS 够用， 但能让 Office / Finder 保存时不拒绝写入）。 只读模式下浏览下载正常，写操作一律 403。

06

网页端：桌面隐喻 + 布局记忆

打开网址就是一个「桌面」：图标、任务栏、可拖拽可缩放的窗口。

窗口系统

  • 可以同时开多个「文件管理」窗口，窗口之间能直接拖拽搬运文件。
  • 窗口标题跟着当前目录走，任务栏显示所有窗口并可最小化/切换。
  • 右键有完整菜单：预览、下载、复制/剪切/粘贴、创建副本、复制到…、分享、重命名、删除。
  • 上传是队列化的：可以一次拖很多文件，面板里显示进度与结果。
  • 支持 ⌘K 全局搜索，命中关键词高亮，点结果直接跳到所在目录。

布局记忆

网页会记住你开着哪些窗口、各自的位置与大小、层叠顺序， 以及每个文件管理窗口停在哪个卷的哪个目录。下次打开网页或重新登录，自动还原， 不用每次重新摆一遍。

  • 状态存在浏览器本地（localStorage），保存在服务端的只有你的文件。
  • 关网页、切到后台、退出登录前会立刻落盘，最后的拖动也不会丢。
  • 任务栏右侧的图标可以随时关掉记忆，关掉时同时清掉已保存的布局。
  • 换屏幕尺寸后恢复会做边界收敛，窗口不会跑到看不见的地方。
07

预览：只用系统自带能力，什么都不用装

照片、视频、PDF、文本、Word、表格、幻灯片，桌面和分享页都能直接看。

文件类型怎么预览说明
图片（jpg / png / heic / webp …）直接给原图可切换「适应窗口 / 原始尺寸」
视频 / 音频（mp4 / mov / mp3 / flac …）浏览器原生播放器走 Range，可拖动进度、边下边播
PDF浏览器内置阅读器沙箱 iframe
文本 / 代码 / CSV / JSON / Markdown服务器读出文本UTF-8 → GB18030 → Latin-1 兜底，中文老文件也能看
Word / RTF / ODTtextutil 转成 HTML段落与表格都保留，放进沙箱 iframe（脚本被禁用）
Excel / PPT / Pages / Keynote …qlmanage（系统 QuickLook）出图显示第一页的渲染图，完整内容请下载后用对应软件打开

转换结果按内容哈希缓存：同一个文件第二次打开是瞬时的；缓存超过 256MB 会自动清理最旧的。 转换进程都有硬超时，卡住的进程会被结束，不会把服务器拖死。

08

分享链接：给文件或文件夹发一个地址

对方不需要账号，打开网址就能浏览、预览、下载。

怎么做的

  • 每次分享生成一个随机 token，链接形如 /s/<token>。
  • 可以设访问密码；校验通过后只发一个带哈希的 Cookie，密码本身不落 Cookie。
  • 可以设有效期，或选择永久有效。
  • 分享文件夹时，访问范围被限制在该目录内 —— 请求别的路径会被拒绝。
  • 分享页同样可以使用预览与下载，界面和桌面端用同一套渲染逻辑。
  • 随时可以撤销；撤销后链接立即 410。

边界在哪

分享链接只能读。上传、改名、删除这些能改变数据的操作在分享页上不存在， 接口也不接受 —— 一条链接泄漏了也只是泄漏了它指向的那些文件。

账号密码与端口只能在 Mac 应用里修改，网页端（包括分享页）没有任何入口可以改它们。

09

安全与隐私

你的文件始终在自己的机器上。

数据不出本机

没有云、没有账号体系、没有遥测。文件存在你选的目录里，服务只在你指定的端口上监听。

密码只存哈希

账号密码用 PBKDF2-HMAC-SHA256（随机盐 + 10 万次迭代）保存，不保存明文； 改密码会注销所有网页登录。

WebDAV 走明文

WebDAV 使用 HTTP Basic 认证，密码在局域网内是明文传输。 建议只在可信网络里开启，或自行加一层 HTTPS 反向代理。

照片收集

生成一条链接发给朋友，他们不用注册登录就能上传照片，可以限制单个文件大小与总量、设有效期与密码。 收集链接只进不出：访客看不到也下载不了已收到的照片；同名照片自动改名。

格式 v2：追加日志

改动只往 info/index.log 追加一小段，不再每次重写整份索引。实测 5,000 个文件：单次写入 74.5ms → 5.6ms，写 5,000 条 173 秒 → 14 秒。 老目录不会被自动升级，旧版软件打开 v2 目录只读，结构始终不变。

10

怎么确认它真的可靠

所有关键行为都有自动化测试守着，包括「磁盘结构不许变」这种约束。

核心自测

Tools/e2e/selftest

密码哈希兼容老配置、SHA-256 标准向量、路径穿越与非法名称、磁盘格式约定， 以及一条性能守卫：PBKDF2 单次必须小于 150ms，否则 Finder 挂载会超时。

接口行为测试

Tools/e2e/run.sh

上传去重、覆盖不丢记录、改名、删除与引用计数、跨卷复制移动、搜索、分享范围与密码、 WebDAV 全套方法与只读模式、重启后自动读回记录。

界面与稳定性

Tools/e2e/webui.sh · stability.sh

用系统 WebKit 真正渲染网页，做点击命中测试、拖拽搬运、搜索、布局记忆、预览； 稳定性套件则反复读写并校验索引不损坏。

一句话总结

MacNas 把「内容」和「名字」拆开：内容按哈希只存一份，名字和目录结构放在一份可演进、 可重建、永不破坏兼容的索引里。磁盘结构被冻结成契约，所以升级永远不需要你搬数据； 去重发生在最底层，所以复制不占空间、改名移动不搬字节。
