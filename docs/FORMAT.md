# MacNas 磁盘格式契约（v1）

> 这份文档是**承诺**：后续任何版本的 MacNas 都不得违反。目标是
> 「升级软件不改变系统结构，也不让已有数据失效」；降级运行也不会破坏新版本写入的数据。

## 1. 目录结构（冻结）

一个“卷”就是用户选择的一个文件夹，里面**永远只有两个子文件夹**：

```
<卷根>/
├── document/                         内容区
│   └── blobs/<哈希前2位>/<哈希>[.<扩展名>]
└── info/                             记录区
    ├── index.json                    全部文件记录
    ├── index.json.bak                上一次的完好索引（自动维护）
    └── volume.json                   卷身份（id / 名称 / 格式版本）
```

规则：

- 这两个文件夹的**名字、层级、含义永不改变**，不得改名、移动或删除。
- 新功能只能在这两个文件夹**内部新增**文件或子文件夹（例如将来可能在
  `document/` 下新增 `thumbnails/`、在 `info/` 下新增 `journal/`）。
- 老版本遇到自己不认识的子文件/子文件夹时必须**忽略**，不得删除或报错。
  当前实现只读写上面列出的文件，`pruneOrphans` 也只在 `document/blobs/` 范围内清理。

## 2. 文件命名（内容寻址）

- 物理文件名 = 内容的 SHA-256（十六进制小写），前 2 位作为分片目录。
- 扩展名只是方便人看，**不参与身份判定**；`storageRelPath` 才是权威路径。
- 因此即使记录丢失，也能从文件名反推出哈希，重建全部记录并正常下载（见 §5）。
- 相同哈希的内容在**所有卷里只存一份**；其它记录通过
  `storageVolumeId` + `storageRelPath` 指向那一份。

## 3. 字段规则（只增不改）

各文件的字段：

| 文件 | 字段 |
| --- | --- |
| `index.json` | `version`, `formatVersion`, `volumeId`, `volumeName`, `updatedAt`, `folders`, `entries` |
| `entries[]` | `id`, `name`, `sha256`, `size`, `logicalPath`, `storageVolumeId`, `storageRelPath`, `createdAt`, `source` |
| `volume.json` | `app`, `version`, `formatVersion`, `id`, `name`, `createdAt` |
| `config.json` | `version`, `formatVersion`, `initialized`, `username`, `passwordSalt`, `passwordHash`, `port`, `volumes`, `autoStartServer`, `webdavEnabled`, `webdavReadOnly` |

- 已有字段的名称、含义、取值**永不改变**；不得复用某个字段名去表达新含义。
- 新增字段必须**可以缺省**：读不到时用默认值（所有解码路径都是宽容解码，
  缺字段、类型不符、甚至某条记录畸形，都不会让整份索引读不出来）。
- 删除字段时，字段可以不再使用，但**不能把它从文件里抹掉**（见 §4）。

## 4. 未知字段原样保留

老版本读到新版本写入的未知字段时，会在**下一次写回时把它们带回去**：

- 顶层未知字段、以及每条记录的未知字段（按 `id` 匹配）都会被保留。
- 因此“新版本写 → 老版本改一次 → 再回到新版本”不会丢失任何信息。
- 实现见 `MacNas/Core/Schema.swift` 的 `JSONPreservation` 与 `IndexFile`。

## 5. 版本与只读保护

- `formatVersion` 表示这份数据由哪一代格式写成，当前为 `1`。
- 有效版本 = `max(volume.json.formatVersion, index.json.formatVersion)`。
- 版本高于当前软件能读的最高版本时：该卷以**只读**方式打开
  （可浏览、可下载），所有写操作返回 `409` 并提示升级，
  **不会改写卷内任何文件**（包括 `volume.json`、`index.json`）。
- 低版本数据升级：只做“补默认值 / 加字段”的迁移（`SchemaMigration`），
  迁移前强制备份一份 `index.json.bak`，且迁移不会改变目录结构。

## 5.5 应用级文件（不属于任何卷）

`~/Library/Application Support/MacNas/` 下还有两个**应用级**文件，它们不在卷里，
所以增删它们不影响任何卷的结构：

| 文件 | 内容 |
| --- | --- |
| `config.json` | 账号、端口、目录列表 |
| `shares.json` | 分享链接（token、目标、有效期、密码哈希、访问计数） |

这两个文件同样遵守 §3 的字段规则与 §4 的未知字段保留。

## 5.5 回收站与历史版本（同样是只增字段）

删除默认**不销毁内容**，而是把记录移入索引里的 `trashed` 数组：

- 顶层新增 `trashed: [FileEntry]`，元素结构与 `entries` 完全一致，另加两个可选字段
  `trashedAt`（进回收站时间）与 `originalPath`（原位置，用于还原）。
- `entries` 里的记录新增可选字段 `history: [FileVersion]`，覆盖上传时把旧内容记成历史版本
  （`{sha256, size, createdAt, replacedAt, name}`），最多保留 20 版。
- **引用计数把三处都算上**：正常记录、每条记录的历史版本、回收站里的记录。
  只有三处都不再引用某个哈希，`document/blobs` 里的那份内容才会被删除。
- 老版本软件读到这些字段会原样保留（未知字段机制），因此**新旧版本可以交替打开同一个目录**。

## 5.6 WebDAV 与磁盘结构的关系

WebDAV（`/dav`）**不改变磁盘结构**：它只是把 `info/index.json` 里的逻辑目录树按 WebDAV 协议暴露出来，
读写最终都走同一套 Store 逻辑（上传→哈希→去重→写记录）。
所以通过 WebDAV 做的任何操作，在磁盘上仍然只产生 §1/§2 描述的那两种文件夹与哈希文件。

## 5.7 追加日志（formatVersion 2）

v2 相对 v1 **只多了一个文件**：`info/index.log`。目录结构、字段含义、其它文件全部不变。

### 为什么要它

v1 的做法是：任何一次改动都把整份 `index.json` 重写一遍。索引越大写得越慢，是 O(文件数) 的开销。
实测（5,000 条记录）：

| | 单次写入 | 写入 5,000 条总耗时 |
|---|---|---|
| v1 整份重写 | 13.9ms → **74.5ms**（随记录数线性增长） | **173 秒** |
| v2 追加日志 | 1.1ms → **5.6ms** | **14 秒** |

按 v1 的趋势，10 万条时每次写入要 ~1.5 秒；v2 把这个常数压掉了一个数量级。

### 日志格式

`info/index.log` 是**按行分隔的 JSON**，一行一条改动记录：

```json
{"at":"2026-10-06T04:00:00Z","put":[<完整记录对象>],"remove":["id"],"folders":["/","/项目"],"putTrash":[],"removeTrash":[]}
```

- `put` / `putTrash`：新增或修改的记录，**整条**写入（回放时按 `id` 覆盖，天然幂等）。
- `remove` / `removeTrash`：被删除的记录 id。
- `folders`：文件夹列表**只在变化时**写完整快照（文件夹本身很轻）。

### 读写规则

- **读**：先读 `index.json`（失败则退回 `index.json.bak`），再把 `index.log` 里的记录按顺序回放。
  损坏的行（例如断电写了一半）会被**跳过**，不影响其它记录；下次写入时会自动压缩修复。
- **写**：改动只追加一行；日志超过 **4MB** 时压缩一次 —— 写出一份完整 `index.json` 并删掉日志。
- 压缩后的 `index.json` 与 v1 完全同构，只是 `formatVersion` 是 2。

### 实测规模（20,000 条记录，Release 优化构建）

| 指标 | 数值 |
|---|---|
| 单次写入（第 1 千条 / 第 2 万条） | 0.70ms → **11.8ms** |
| 连续写入 20,000 条总耗时 | **123 秒**（v1 整份重写按趋势约需 1.5 小时） |
| 装载（快照 + 回放日志） | 282ms |
| 日志压缩回整份快照 | 289ms → 快照 10MB |
| 列目录 / 空间分析 | 32ms / 17ms |

写入仍然随记录数线性增长（剩余的那部分是「找出这次改了哪几条」的扫描，约 0.6µs/条），
按趋势推算 10 万条约 60ms/次、装载约 1.4s。如果将来真的到了几十万文件还嫌慢，
下一步是让每次改动显式带上「改了哪些 id」（把这次扫描也去掉），再往后才需要按哈希前缀分片。
两者都会通过新增字段/新增文件实现，不改动已有结构。

### 版本策略（重要）

- **已有目录永远不会被自动升级**：v1 目录继续用 v1 的写法，直到用户在软件「设置 → 写入性能」里点「启用快速写入」。
  这样「换回旧版软件」不会突然失去写入能力。
- **新建目录默认就是 v2**。
- 旧版 MacNas（只认 v1）打开 v2 目录时，按契约第 4 条**只读打开**：可以浏览、下载、预览，一个字节都不会改。
- 升级动作只做两件事：把 `formatVersion` 写成 2、把当前索引整份落盘一次，然后删掉可能残留的日志。

## 5.8 分享记录里的收集链接（photos collect）

分享记录（`shares.json`，位于软件支持目录而不是卷里）新增了可选字段，全部只增不改、缺省即旧行为：

| 字段 | 含义 |
|---|---|
| `kind` | 新增取值 `"collect"`（照片收集；原有 `"file"` / `"folder"` 不变） |
| `allowUpload` | 是否允许访客上传 |
| `maxFileBytes` | 单个文件上限，`0` 表示不限 |
| `maxTotalBytes` | 这条链接累计可接收的总字节，`0` 表示不限 |
| `uploadedBytes` / `uploadedCount` | 已接收的字节数与张数 |
| `imagesOnly` | 是否只收图片/视频 |

收集链接的语义约定：

1. **只进不出**：`GET /api/pub/<token>` 对收集链接只返回额度与状态，**不返回任何已收文件的名字或列表**；也不提供下载入口。
2. 访客通过 `POST /api/pub/<token>/upload?name=…` 上传，免登录；有密码时需要先 `POST /api/pub/<token>/auth`。
3. 额度在**服务端**强制：超过单文件上限 → `413`；总量不足 → `507`；文件类型不符（`imagesOnly`）→ `415`；文件名带路径分隔符 → `400`。
4. 重名自动改名（`名字 (2).ext`…），不会因为重名让访客上传失败。
5. 照片按普通文件走同一条存储管线：内容哈希去重、进回收站、可预览，与在软件里上传完全一致。

## 6. 数据安全与恢复

| 场景 | 行为 |
| --- | --- |
| 写入过程中断电 | 索引原子写入（临时文件 + rename），不会写出半截文件 |
| `index.json` 被外部改坏 | 自动回退到 `index.json.bak` 并写回修复 |
| `index.json` 与备份都没了 | 按哈希从 `document/blobs` 重建记录（命名为 `recovered-<哈希前8位>.<扩展名>`） |
| 内容被移到别的卷/目录 | 按哈希全盘找回并修正记录里的实际位置 |
| 记录里的内容缺失 | 标记为“缺失”，在目录详情里提示，不静默丢记录 |
| 删掉一个副本 | 引用计数减一，只有最后一条记录消失才删除物理内容 |
| `document/blobs` 里有游离文件 | 「清理孤立文件」手动清理（不会自动删） |

**恢复能力的关键前提**：物理文件名始终是内容哈希 —— 所以 §2 的命名约定同样属于契约。

## 7. 给后续版本的检查清单

修改存储相关代码时，逐条确认：

- [ ] 没有新增第三个顶层子文件夹？没有改 `document` / `info` / `blobs` 的名字？
- [ ] 没有改变任何已有字段的名称或含义？新字段都可缺省？
- [ ] 老版本读新数据时，未知字段会被写回（新字段已登记进 `SchemaFields`）？
- [ ] 新版本写出的 `formatVersion` 已递增，并且老版本会只读打开？
- [ ] 迁移只做加法，且迁移前有备份？
- [ ] `./Tools/e2e/run.sh` 与 `./Tools/e2e/stability.sh` 全部通过？
